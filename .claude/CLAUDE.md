# 项目规范（Grade-your-homework）

本文件是项目级规范，优先级高于全局规范，每次会话自动加载。代码与项目的具体规则以本文件为准。

## 代码结构化（硬约束）

代码按模块分文件夹组织，禁止在根目录堆放业务文件：

| 目录 | 职责 |
| --- | --- |
| app/ | 路由与请求处理 |
| services/ | 业务逻辑（评分、OCR、语义匹配） |
| utils/ | 通用工具 |
| tests/ | 测试 |

硬性规则：

1. 一个文件不超过 5 个公开函数或方法。
2. 一个文件不超过约 200 行，超出拆分为多个文件。
3. 每个 Python 包目录含 __init__.py。
4. 根目录只保留入口 run.py 与配置，业务代码一律位于 app/services/utils 分层目录。

## 代码风格

1. Python 严格遵循 PEP 8，含类型注解与 docstring。
2. 变量名、函数名用英文 snake_case，类名用 PascalCase。
3. 代码标识符用英文，注释根据上下文用中文。

## 测试风格

1. 使用 pytest。
2. 命名 test_功能_场景。
3. 每个核心函数或模块有单元测试。
4. 外部依赖（DeepSeek API、OCR 模型）必须 mock，测试可离线独立运行。

## 复用习惯

1. 重复逻辑抽为工具函数。
2. 常量集中在 config 模块。
3. 优先使用成熟第三方库，避免重复造轮子。

## 版本号

采用语义化三段：主版本.次版本.修订。重大重构升主版本、新功能升次版本、bugfix 升修订。当前版本 2.3.0。

## Git 工作流

两层分支：main 永远可运行；每轮迭代从 main 开版本分支；版本内任务多时开任务分支。

1. 每轮迭代必须开版本分支 version/x.y.z，不在 main 直接开发。
2. 版本内子任务较多（≥3 个）时，为每个子任务开任务分支 task/<编号>，单测通过后 merge --no-ff 回版本分支。
3. 版本分支联调通过后 merge --no-ff 回 main。
4. 允许执行：branch、checkout -b、commit、merge --no-ff（无冲突时）。
5. 禁止执行：push、reset --hard、checkout --；merge 产生冲突时停下，交给用户处理。

## 工作原则（fail fast）

1. 小步提交、频繁测试，让错误尽早暴露。
2. 测试要能立即失败，不写宽松或形同虚设的断言。
3. 不吞异常、不塞默认值，让错误浮出水面（禁止旧版 return 0.5 式过度防御）。
4. 尽早集成，不把联调留到最后。
5. 实现细节不确定时及时向用户确认，不猜着写。

## 工程约束

1. 完成标准（DoD）：单测通过、集成联调通过、迭代反馈表已更新、已提交，四者同时成立才算完成；代码改动未同步 README/requirements 不算完成。
2. 回滚保护：联调失败且短时间修不好时，回退到上一版本 commit，保持 main 可运行。
3. 环境冒烟：每轮开始先在 ggrade 环境跑 python -c "from app import create_app" 确认环境就绪。
4. 性能基线：涉及性能的任务先记录优化前基线，再优化。
5. 依赖同步：新增/移除依赖时同步 requirements.txt 并验证可安装。

## 迭代流程

每轮迭代通过 /loop skill 执行，流程定义见 memory/循环/工作循环.md。每轮结尾把迭代反馈表中"已完成"条目移入 memory/问题与优化反馈/已完成迭代反馈表.md，活跃表只留待处理/进行中/已延后。
